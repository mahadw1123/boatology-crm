# Boatology CRM — Production Hardening Audit (Phase 1)

Produced against the "Boatology CRM — Final Hardening & Production Implementation Plan" spec. This is a factual audit of the current codebase, not a proposal — every claim below is sourced from the actual code (file:line references preserved from the underlying research).

---

## A. Current Architecture Summary

**Stack**: React/Vite + tRPC + Drizzle ORM over a single SQLite file. No separate backend service — Express hosts both the API and (in production) the built frontend.

**Auth today**: Stateless JWT (HS256, `jose`), bcryptjs password hashing, 14-day token expiry in a 30-day httpOnly cookie (mismatch: cookie outlives token). No session table — a `sessionVersion` integer on `users` is the sole server-side revocation mechanism, incremented on logout, `relinkCustomer`, and `updateUserRole`. `users.openId` is the closest thing to a stable ID, but it's synthesized as `local:${email}` at creation — still email-derived, not a true provider-issued permanent ID. `users.email` has **no DB-level unique constraint** — uniqueness is only enforced by app-side check-then-insert (a real, if narrow, race condition). There is currently no `changeEmail` mutation anywhere, so the "email change should not affect identity" risk the spec worries about is **not yet exploitable** — but also not yet guarded against, since the capability doesn't exist to guard.

**Role assignment**: Bootstrap-admin is atomic (SQLite transaction, `COUNT(*) = 0` gate) and single-use — not a general "first user" fallback. Self-registration is hardcoded to `role: "customer"`. Staff invites carry the role; acceptance reads it from the invite record, not user input. One narrow auto-link-by-email exists (technician invite acceptance matches an existing `employees` row by email) — customer self-registration explicitly does **not** auto-link, with an inline comment stating this is deliberate.

**Workflow logic**: No centralized state-machine. Quote/invoice/job status transitions are validated inline, per-mutation, in `server/routers.ts`. The single most important rule — "quote must be `sent` to accept/reject" — is independently re-implemented in **three places** (`routers.ts:1270`, `db.ts:301`, `db.ts:285`). They currently agree with each other, but nothing enforces that they keep agreeing as the code evolves. Deposit-invoice creation (`acceptQuoteAndEnsureDeposit`) is the one truly hardened operation in the codebase: real `sqlite.transaction()`, idempotency re-check inside the transaction, covered by an actual test. Job eligibility is ad-hoc inline logic in `jobs.create`, not a reusable function, and correctly checks the deposit invoice's *status* — but there's also an unused `jobs.depositReceived` boolean that can silently drift from reality since nothing keeps it in sync.

**Stripe**: The strongest integration in the codebase. Webhook handling is idempotent via a unique `stripeWebhookEvents.eventId` constraint, PaymentIntent creation uses a real Stripe idempotency key, and the webhook handler is genuinely partial-failure-safe — the paid-status DB write commits before the receipt email is attempted, so an email failure can't roll back a real payment. What's missing: no reconciliation mechanism at all. `markPaidManually` is a blind override that never queries Stripe; there's no scheduled or on-demand "diff Stripe against Boatology" job.

**Resend**: Centralized in one function (`sendEmail()` — confirmed the only caller of Resend's API anywhere). Quotes and invoices track `emailStatus`/`emailError`; jobs do not — five job-related send sites just `console.error` on failure with zero persisted state on the job record.

**Xero**: Not idempotent. Neither `createXeroQuoteForQuote` nor `createXeroInvoiceForJob` checks the existing `xeroQuoteRef`/`xeroInvoiceRef` before POSTing — double-clicking "Sync to Xero" **will** create a duplicate Xero-side record today. No `lastSyncError` field; failures aren't even routed through the app's own generic error-capture system (`captureSystemError`), unlike Stripe and email failures, which are.

**Task/reminder engine**: Effectively doesn't exist. There's a `staffTasks` table with an `autoGenerated` flag, but exactly one call site actually auto-creates a task (material request → approval task), no deduplication key, no escalation, no due-date engine, no rules beyond that single case.

**Permissions**: No capability/permission model — 74+ inline `ctx.user.role !== "..."` checks and 200+ `FORBIDDEN` throws scattered across `routers.ts`. Encouragingly, every ownership-sensitive `getById`-style endpoint that was audited (customer↔quote, customer↔invoice, customer↔job, technician↔job, customer↔vessel, documents) does enforce server-side ownership — no confirmed hole. But it's 200+ independent copies of "did I check this correctly," not one shared guard.

**Testing**: One real test file, 8 tests, covering login, quote-accept idempotency, customer/technician data isolation, Stripe webhook idempotency, and error deduplication. A separate Playwright E2E script exists but isn't wired into `npm run verify` and has no config file checked in.

**Environment separation**: None beyond whatever `.env` values an operator sets. Single SQLite file, no code-level dev/prod branching. `server/start-production.ts` is 4 lines and does nothing protective. `db:seed` does refuse to run when `NODE_ENV=production` (a real, working guard) — that part already matches the spec's intent.

## C. Files/Modules That Would Need Modification (by theme)

- **Auth migration (if WorkOS approved)**: `server/_core/auth.ts`, `server/_core/requireAuthUser.ts`, `server/_core/trpc.ts`, `server/_core/cookies.ts`, `drizzle/schema.ts` (`users` table), every `ctx.user` consumer in `server/routers.ts` (i.e., nearly the whole file), `src/pages/Login.tsx`, `src/pages/AcceptInvite.tsx`, `src/pages/SetupAdmin.tsx`, `src/_core/hooks/useAuth.ts`.
- **Permission model**: new `server/_core/permissions.ts` (capability table + `requirePermission()` helper), then a mechanical pass over every procedure in `server/routers.ts` to replace inline role checks — high line-count, low conceptual risk if done incrementally per-router.
- **Workflow state machine**: new `server/_core/workflow/` module (`quoteTransitions.ts`, `invoiceTransitions.ts`, `jobTransitions.ts`, `jobEligibility.ts`), then refactor `routers.ts` quote/invoice/job routers and `db.ts`'s `acceptQuoteAndEnsureDeposit`/`rejectQuoteIfSent` to call the shared validators instead of inlining checks.
- **Stripe reconciliation**: `server/_core/stripe.ts` (add a list/diff function), `server/_core/scheduler.ts` (register a reconciliation job), new admin UI card in `src/pages/Administration.tsx`.
- **Xero idempotency**: `server/_core/xero.ts` (`createXeroQuoteForQuote`/`createXeroInvoiceForJob` need a pre-check against the stored ref before POSTing), add `lastSyncError`/status columns, route failures through `captureSystemError`.
- **Task engine**: new `drizzle/schema.ts` table, new `server/_core/tasks/` module (rule engine, dedup-key logic, escalation), dashboard components in `src/pages/`.
- **Audit log expansion**: add `logAuditEvent` calls to creation paths currently missing them in `server/routers.ts`.
- **Environment separation**: `server/_core/env.ts`, `server/migrate.ts`, `server/seed.ts`, deployment scripts/docs.

## D. Database Migration Plan (additive, in likely order)

1. `users.email` → add unique constraint (requires a data-cleanup migration first if any duplicate/null-collision rows exist — needs a check before applying).
2. `invoices` → unique constraint or partial index on `(quoteId, invoiceType)` where `invoiceType = 'deposit'`, to make deposit-idempotency a real DB guarantee instead of only an app-level re-check.
3. `invoices` → add `depositPercentageUsed` (real, nullable) for historical accuracy.
4. `jobs` → decide: either enforce one-job-per-quote via a unique constraint on `quoteId`, or explicitly design multi-job-per-quote as intentional (spec §20 flags this ambiguity directly — needs your decision, not just code).
5. `xero`-tracking → add `xeroSyncStatus`/`xeroLastSyncError` columns to `quotes` and `jobs` (or a shared `xeroSyncLog` table).
6. New `tasks_v2` (or similar) table for the real task engine — deliberately not reusing existing `tasks`/`staffTasks` names to avoid confusion with the technician-checklist and manual-office-todo tables that already use those names.
7. If WorkOS is approved: `users.authProviderId` (unique), migration to backfill from existing accounts, deprecation path for `passwordHash`/`openId`.
8. If environment separation is approved: no schema change needed, just deployment/config — two separate DB files, one per environment.

## E. Recommended Implementation Order

Your spec's own phase order (69) is sound, but phases 3 (WorkOS) and 22-32 (task engine) are each substantial standalone projects, not quick add-ons — realistically weeks each, not part of a single session. My recommended sequencing, given what the audit actually found:

1. **Stability + quick wins with no architectural decisions required**: DB constraints (D.1-D.3), Xero idempotency fix (this is a live bug, not a hardening nice-to-have), job-email status tracking, audit log gaps. Low risk, no design decisions needed from you.
2. **Workflow state machine centralization**: consolidate the 3x-duplicated quote-transition rule and the ad-hoc job-eligibility check into shared, tested functions. Medium effort, no external dependencies, meaningfully reduces the exact risk class (drift between duplicated rules) the spec worries about.
3. **Permission model**: mechanical but large refactor of the 74+ inline checks into a declarative table. High line-count, should be done router-by-router with tests, not all at once.
4. **Stripe reconciliation**: build the admin-facing "check Stripe status" + scheduled diff job. Self-contained, no dependency on 1-3.
5. **Task/reminder engine**: genuinely new subsystem. Depends on the workflow state machine (step 2) existing first, since task rules key off state transitions.
6. **WorkOS migration** — deliberately last, and only if you decide to proceed (see risk F.1). Touches nearly every file that reads `ctx.user`, so it should happen once the codebase around it is already stable, not while things are still shifting.
7. **Environment separation, system health page, full test suite expansion** — can run in parallel with 4-5 once 1-3 are done.

## F. Risks

1. **WorkOS migration is the highest-cost, highest-risk item in the entire spec**, and the current auth system, while not matching the spec's ideal, is not actually broken — bootstrap is atomic, invite-based role assignment has no fallback holes, session revocation works, and ownership checks are consistently enforced everywhere audited. Before committing to WorkOS, worth deciding: is the goal "provider-managed MFA/SSO/recovery" (a real WorkOS benefit) or "a stable permanent user ID" (achievable with a much smaller change — add a DB-unique `email` constraint and stop deriving `openId` from email, no third-party dependency required)?
2. **The permission-model refactor touches the single largest file in the codebase** (`routers.ts`, 5000+ lines) — doing it in one pass risks introducing exactly the kind of authorization regression the spec is trying to prevent. Needs to be incremental, router-by-router, each step covered by a permission test before merging the next.
3. **Job-per-quote uniqueness (D.4) is a business-rule decision, not an engineering one** — I can't determine from the code alone whether multiple jobs from one quote is ever intentional (e.g. a quote covering multiple separate work phases). This needs your answer before a constraint is added.
4. **The existing test suite, while small, is genuinely well-targeted** (real idempotency/isolation assertions) — any refactor of the areas it covers (quote accept, webhook handling, technician scoping) should keep those exact tests green throughout, not just at the end.
5. **Xero idempotency fix should happen soon regardless of the rest of this plan** — it's a live, confirmed duplicate-record bug in production-facing code, not a theoretical hardening gap.

## G. Existing Functionality That Must Not Regress

- Stripe webhook idempotency (unique `eventId` constraint) and PaymentIntent idempotency key generation.
- The webhook handler's partial-failure-safety (paid status commits before email is attempted).
- `acceptQuoteAndEnsureDeposit`'s real transaction + idempotency re-check — this is the one place in the codebase already built to the spec's standard.
- Server-side ownership checks on every customer/technician-facing `getById`-style endpoint.
- `sessionVersion`-based logout/role-change/relink invalidation.
- Bootstrap-admin's atomic single-use guard.
- Staff-invite role assignment (admin-issued only, no self-selected role).
- `db:seed`'s existing production guard.
- The 8 existing tests in `tests/core-workflow.test.ts` — all currently passing, all asserting real behavior worth protecting.
- The recent fixes from this session (welcome email, quote revisioning, job cancellation, technician notifications, audit log filters, CSV import for material requests/time entries, send-test-email) — none of these were touched by this audit and should remain intact through any of the above work.
